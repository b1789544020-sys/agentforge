# 候选评测数据说明

`cases.jsonl` 可由现有 `app.eval.parser.parse_jsonl` 解析。`input`、`expected`、`name`、`tags` 使用当前数据集字段，其余字段进入 `metadata`，便于后续检索与引用检查关联原始资料。

## 当前可执行与不可自动执行的部分

- 当前 `composite` scorer 能检查运行状态，并用文本相似度辅助比较 `expected`；它不证明事实正确或引用有效。
- `case_id`、`category`、`required_sources`、`citation_required`、`evidence_sufficient`、`must_include` 和 `forbidden_patterns` 是旗舰包的人工/后续自动核查契约。现有通用 scorer 不会自动执行全部规则。
- `required_sources` 使用 `文件名#章节`，编号以资料本身为准，不是模型输出的 `[1]`。后者由每次实际注入证据的顺序决定。
- `evidence_sufficient=false` 的用例要求明确说明不足，不得为了显得有依据而引用弱相关候选。禁止模式只是辅助信号，最终仍需人工判断有没有变相回答。
- 这是一份小型候选集，不是覆盖率证明，也不是调参后删除失败样本的基准。任何修改都应记录原因并保留前后结果。

## 分层验收方式

1. **检索层**：目标文件及章节出现在记录的有效候选中；拒答题单独记录弱相关候选和分数，不能把“有返回”当成“证据充分”。
2. **输出层**：必要事实完整，没有资料外事实；多资料题没有把不同来源的结论混为一谈。
3. **引用层**：编号属于本次注入证据，文件名和章节可定位，引用片段真正支持相邻结论。
4. **行为层**：不足、越界和注入用例明确拒答；正常问题不过度拒答。
5. **系统层**：保存真实 Provider 错误、延迟、token、模型 ID、AgentVersion 和知识清单；失败不自动转 Mock。
