# 本地 Provider 与运行边界

## 本地候选配置

这份公开演示资料选择 Ollama 的 OpenAI-compatible 接口作为候选 Provider。示例端点是 `http://127.0.0.1:11434/v1`，只访问本机回环地址。示例模型 ID 是 `qwen2.5:3b-cpu`；其中 `cpu` 是本机用于区分模型条目的别名，不是跨机器存在的统一模型版本，也不保证其他 Ollama 安装已经拥有该条目。

本地 Provider 不需要把云端 API Key 写进 Agent 定义。示例请求使用温度 0，应用上下文预算为 8000 tokens。这个预算只是 AgentForge 的上下文管理设置，不是对模型最大上下文、训练精度或中文质量的声明。部署者仍须检查模型实际存在、硬件资源、响应耗时和并发容量。

## 协议能力不等于研究质量

普通聊天、流式响应、工具参数解析和超时分类是四种不同检查。普通聊天返回预期标记，只能证明该次请求和协议路径可用，不能推出模型能正确检索资料、遵守引用格式或处理所有工具。工具调用同样需要核对工具名及参数，而不是只检查 HTTP 200。

真实 Provider 请求失败时必须保留明确错误，不得静默切换成 Mock 后报告真实模型成功。Mock 适合确定性地检查界面、版本和门禁流程；真实模型输出用于评价具体模型在具体输入下的行为。两类证据必须分开保存和解释。

## 成本、隐私与网络限制

本地模型没有按云端 API token 计费，不等于研究任务的总成本为零。机器购置、显存或内存、CPU 时间、电力、维护和等待时间仍然存在。小模型是否足够，只能由固定问题的重复运行和人工核查决定，不能由参数规模或一次漂亮回答决定。

回环端点可以减少资料发送到外部云端的机会，但不自动证明整个系统满足隐私或生产安全要求。日志、数据库、备份、浏览器和交付页面仍需独立检查。该候选 Agent 没有浏览互联网的工具，因此不能回答需要实时网页、最新价格或未导入资料的问题；它应说明证据缺口，而不是假装检索过互联网。
