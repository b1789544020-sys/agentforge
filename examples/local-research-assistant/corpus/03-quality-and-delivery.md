# 质量、比较与交付

## 不可变版本与同输入比较

每次明确保存 canonical Definition 会产生新的 AgentVersion。调试请求可以指定 `agent_version_id`，使运行对象与记录版本一致。A/B 比较必须给两个版本完全相同的用户输入，并分别保存输出、状态、延迟、token 和 Trace。历史版本的运行不应覆盖当前 Agent 草稿。

同一输入得到不同答案，只能说明两次记录的运行行为不同。差异可能来自 Prompt、模型、资料、检索、工具或非确定性，不能自动归因于某一处修改，更不能把单次差异当成真实模型质量提升。模型或资料改变时，应在比较条件中明确标注。

## 测试、评分与门禁

固定评测套件用于重复检查明确选定的用例。现有文本相似度可以辅助比较参考答案，但它不等于事实正确、引用有效或证据充分。检索是否召回目标资料、引用是否支持结论、应拒答时是否拒答，需要独立的检查和人工抽查。

质量门禁应绑定固定 AgentVersion 和固定用例 IDs。只有满足配置的通过条件才进入正常发布路径；管理员 bypass 必须保留原因、人员、时间和审计记录。bypass 是带留痕的治理例外，不会把失败用例变成通过，也不适合用来掩盖尚未解释的模型问题。

## 交付和反馈

Deployment 锁定选定的 AgentVersion，使后续编辑当前 Agent 不直接改变已交付版本。REST、独立页面或 iframe 都只是交付形态，发布前仍需核对运行快照、知识资源、访问控制和目标环境。单机真实模型成功不代表 Docker、多 worker、公网或生产安全已经通过验收。

负面反馈可以先保留原始 Run、版本和用户意见，再由人确认问题、修改预期并加入固定套件。反馈转为候选用例不等于缺陷已经修复；修正 Prompt 或资源后还要生成新版本、重跑相同用例并检查新增回归。只有这些证据齐全，才能描述一次“定位—修复—复测—发布”的闭环。
