# 团队边界与工具安全

## 团队和资源映射

Agent、知识库、Run、评测和交付都需要遵守团队或所有者作用域。界面隐藏一个按钮不是权限边界，后端仍需验证调用者是否能访问目标资源。导入带有知识引用的 Agent 包时，`resource_map` 是把包内逻辑 ref 映射到本地知识库 ID 的显式步骤，不能仅凭同名就自动绑定另一团队的资料。

公开 Agent 包不包含私有文档、历史 Run、用户反馈或 Provider 明文密钥。需要秘密的 Provider 应使用一次性秘密输入或服务端引用，导出和版本 diff 不应暴露明文或密文。本示例使用回环 Ollama，因此没有 required secret；换成云端 Provider 时必须重新检查认证和网络边界。

## 工具选择

研究助理默认不需要 shell、文件写入、任意 HTTP 或 Python 执行。只读工具也要核对实际数据源：`search_knowledge` 在当前 AgentForge 工具注册表中是长期 Memory 查询工具，不是私有 KnowledgeBase 文档检索工具，不能把它返回的记忆当成公开资料引用。

当前候选定义不启用工具，知识上下文由运行器显式检索并注入。后续若要展示受控工具 Trace，应新增或选择真正只读、参数可校验、结果带文档定位的工具，并单独测试正常、空结果、越权、超时和失败路径。不能因为工具有 Trace 就认定它访问了正确资料。

## 内容与交付安全

知识正文和用户问题都可能包含提示注入文字，例如要求忽略规则、披露秘密或调用未授权工具。这些内容应被当作待核查资料，而不是高优先级指令。拒答注入请求不代表系统已经解决所有提示注入问题，仍须结合最小权限、工具白名单和后端授权。

公开交付还需要独立 token、访问控制和限流等保护。示例资料可以公开，不意味着某个部署中的所有知识库都可以公开。跨团队检索、全文读取、导出和交付应分别做权限回归；研究助理的引用不能成为绕过资料权限的旁路。
