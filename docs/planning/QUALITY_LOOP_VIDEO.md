## 1. 视频目标

### 定位

**AgentForge 是一个自托管的 Agent 回归测试与发布门禁平台。**

修改 Prompt、模型或工具后，使用同一批固定用例跨版本回归和比较；达到阈值才发布，并把使用中的失败沉淀为新的回归用例。

短片头文案可采用：

> Agent 能运行，不等于这次修改可以发布。AgentForge 让每一次 Agent 修改都可回归、可比较、可发布。

### 时长与形式

- 主片目标 **8–10 分钟**，内容需要时最多约 12 分钟。
- 不通过重复点击、长时间停顿或逐页朗读凑时长。
- 已实测 PyAgent 正式 MP4 时长为 **120.633 秒**，新片必须长于这一基线。
- 一部完整中文配音主片；另外从主片截取约 20–30 秒无声 GIF 供 README 使用，不另做一套低质量速览。
- RBAC、Providers、知识库、运营、告警和离线部署只作为支撑能力简要出现，不抢占主线。

### 非目标

- 不做全页面功能巡览。
- 不把确定性 Mock 结果描述为真实模型质量基准。
- 不用一部本地演示证明 Docker、Redis、公网安全、多 worker、断网、信创或生产就绪。
- 不承诺反馈转用例等于自动修复，也不承诺回归通过等于任意输入都正确。

## 3. 核心剧情：三个版本，同一套回归

为了真实地同时展示 `new_failure` 和 `fixed`，采用三个版本，而不是勉强让两个版本承担所有差异方向。

| 版本 | 剧情作用 | 必须真实出现的结果 |
| --- | --- | --- |
| v1 稳定基线 | 固定配置、固定用例，建立可比较基线 | 快照、基线 GateRun、达到发布条件；发布 v1 以便后续演示回滚 |
| v2 回归版本 | 修改 Prompt、模型或工具中的一个明确变量 | 同一套件出现失败；相对 v1 准确标出 `new_failure`；答案差异和 Trace 可检查；发布被阻止 |
| v3 修复版本 | 根据失败证据修正配置并追加新快照 | 同一套件重跑；相对 v2 准确标出 `fixed`；确认没有额外新失败；门禁通过并允许发布 |

### 固定比较条件

- 建议使用四个容易理解、结果确定的固定用例；最终数量、名称、输入、expected、scorer 和阈值以排练结果为准。
- v1、v2、v3 的主比较必须使用同一个 `suite_id` 和同一组 `case_ids`。
- 每版只改变剧情要求的配置变量，避免同时修改多项导致无法解释因果。
- 保存并核对版本 ID、GateRun ID、失败用例 ID 和 diff；画面、旁白和 API JSON 必须一致。
- 不在计划阶段预写“两条失败”“50%”为正式成片事实。既有脚本虽采用该例，但正式视频必须记录自己的真实输出。

### 完整闭环

```text
固定 EvalCase → EvalSuite
  → v1 基线 AgentVersion / GateRun / 初始发布
  → v2 配置变化 / new_failure / Trace 与答案 diff / 门禁拦截
  → v3 修复 / fixed / 门禁通过 / 锁定 Deployment
  → 已发布 Agent 的负面反馈
  → 转为 EvalCase 并加入 Suite
  → 回滚到上一已发布版本
  → 新用例进入下一次回归
```

## 4. 分镜与叙事重点

以下时间用于控制节奏，不要求通过加速真实操作或保留空白等待强行对齐。最终时间戳在合成后回填。

| 目标时间 | 真实画面 | 必须讲清楚的内容 | 通过条件 |
| --- | --- | --- | --- |
| 0:00–0:30 | 片头和简洁质量闭环图 | “能运行”与“可以发布”的区别；AgentForge 的定位 | 20–30 秒内进入主题，不堆砌功能名 |
| 0:30–1:30 | Agent 配置、固定 EvalCase、EvalSuite | 演示环境、固定输入、expected、scorer、阈值；醒目标注 Mock | 观众能理解后续比较为何公平 |
| 1:30–2:40 | v1 基线回归、不可变快照、初始发布 | 建立基线；发布 v1 为最终回滚准备上一已发布版本 | 版本、套件、GateRun 和部署关系清楚 |
| 2:40–4:00 | 修改一个配置变量生成 v2，同一套件重跑 | 通过率变化、失败用例、`new_failure`、失败版本不能按正常路径发布 | 失败来自真实运行；套件与用例未偷换 |
| 4:00–5:00 | 失败详情、答案 unified diff、运行 Trace | 哪个输入失败、答案怎样变、Trace 提供哪些定位线索及其局限 | 不只展示红色状态；不编造根因 |
| 5:00–6:10 | 修复后追加 v3，再次运行同一套件 | `fixed`、通过率恢复、没有额外新失败、v3 门禁通过 | v2→v3 和 v1→v3 的关系不被混说 |
| 6:10–7:00 | 发布 v3、Deployment 版本锁定 | 门禁怎样成为发布决定；部署为何绑定固定快照 | 页面状态和后端记录一致 |
| 7:00–8:00 | 调用已发布 Agent、负面反馈、转为 EvalCase | 使用中的失败如何回流；将修正后的 expected 加入指定 Suite | 显示真实新用例及套件关系；明确“回流不等于修复” |
| 8:00–8:35 | 回滚到 v1 | 发布后如何恢复上一已发布版本；历史反馈不因回滚消失 | 回滚目标经过 API 或页面核实 |
| 8:35–9:15 | 闭环回顾、支撑能力和边界卡片 | 版本→回归→门禁→发布→反馈→用例；Mock 与生产边界 | 不以全绿 Mock 结束，不作生产保证 |

### 叙事要求

- 每次转场回答“为什么现在做这一步”，而不是“接下来点击哪里”。
- v2 的失败是剧情需要的真实产品回归，必须完整保留；意外 JavaScript 异常、网络错误或操作失误不能伪装成预期回归。
- 失败定位只陈述 Trace 和输出能够支持的结论。若无法证明具体根因，就说“定位线索”，不说“系统已自动找到根因”。
- 反馈转 EvalCase 后，如界面和性能允许，再运行更新后的套件，证明新用例确实进入后续回归；不得暗示原问题已自动修复。
- 回滚是恢复上一已发布版本，不是删除 v3、修改历史 GateRun 或抹掉反馈。
- 结尾使用“让每次 Agent 修改可回归、可比较、可发布”，同时保留验证边界。

### B. 三版本浏览器闭环

- [ ] 在隔离数据库和端口中创建演示 Agent、固定用例和套件。
- [ ] 保存 v1，确认快照中的 Prompt、Provider、模型、温度、工具和配置。

- [ ] 验证 v3 相对 v2 的 `fixed`，并检查相对基线是否仍有回归。

### C. 门禁、部署和反馈

- [ ] 验证阈值以下、等于阈值、以上三种判定；重判阈值不得重跑模型或篡改原始输出。
- [ ] 验证多个套件状态聚合及 `pending/failed/passed`，只展示与主剧情有关的部分。
- [ ] 发布 v3，核对 Deployment 绑定的 `agent_version_id` 和 RuntimeSpec。
- [ ] 修改当前 Agent 后，已发布 Deployment 仍使用锁定版本。
- [ ] 通过真实交付入口产生一次可解释的负面反馈，保存输入、输出和版本上下文。
- [ ] 仅负面反馈可转换为 EvalCase；人工填写正确 expected，并加入指定 Suite。
- [ ] 检查新用例 ID、反馈的 `eval_case_id`、套件成员和再次转换的限制。
- [ ] 回滚到 v1，核对当前部署版本、历史版本和审计记录。
- [ ] 如演示暂停/恢复或数据持久化，分别执行真实暂停、恢复、页面刷新和服务重启；否则不把它们写入成片结论。

## 6. 录屏与素材组织

### 本机生产目录

正式制作时一次性建立以下结构，不把中间文件散落到根目录：

```text
.scratch/quality-loop-video/
├── evidence/             # 实际命令、退出码、API JSON、浏览器检查
├── recordings/
│   ├── segments/         # 验收通过的分段原始 WebM 与元数据
│   └── rejected/         # 未采用录屏及拒绝原因，本地保留
├── production/           # TTS、字幕边界、剪辑清单和中间视频
├── review/               # 抽帧、音量、解码和隐私检查
└── final/                # 待交付 MP4、SRT、封面和制作报告
```

`.scratch/` 已被项目 `.gitignore` 排除。它用于保持仓库整洁，不表示可以删除原始素材；是否清理本地空间由用户另行决定。

### 隔离与真实性

- 使用独立演示数据库、服务端口和干净 Edge 浏览器上下文，不污染现有数据，不读取真实 `.env` 密钥。
- 演示用例、姓名、输入和反馈内容均自行编写，不使用私人语料或第三方版权材料。
- 采用 Playwright 驱动真实浏览器和真实后端；保存原始录屏、操作结果 JSON、页面异常和控制台错误。
- 录屏只接受核心断言通过的片段。失败尝试保存在 `rejected/`，不能通过改写 JSON 或答案正文获得“成功镜头”。
- 分段录制而不是一口气操作十分钟；通过同一隔离环境和明确状态保持连续性。

### 画面与剪辑

- 主片优先 **1920×1080、H.264、约 30 fps**，保证版本 diff、Trace 和用例 ID 可读；如实际布局不适合，先调整浏览器视口和页面缩放再录制。
- 页面文字不能依赖观众暂停才能辨认。必要时使用克制的局部放大、高亮和章节标签，不拉伸界面。
- 保留创建版本、启动回归、门禁终态、发布、反馈转换和回滚等关键因果动作。
- 加载等待可剪去；真实模型较长等待若被剪掉，用小的“等待已剪辑”提示说明，不能让观众误解耗时。
- 不用快速跳切掩盖中间状态，不在旁白说话时进行观众来不及看清的关键点击。
- 无第三方音乐或影视音轨，默认不加背景音乐，优先保证技术解说清晰。

## 7. 旁白、语音与字幕

### 写作流程

1. 核心流程排练通过后，根据真实版本、界面和结果写最终逐字稿。
2. 逐段检查“画面是否证明这句话”，删除无法证实的形容词和生产承诺。
3. 由执行者自行审核并直接制作，不设置分镜或逐字稿的用户审批环节。
4. 最终采用的逐字稿和实际时间戳回填到本文第 10 节，保证后续能够重建成片。

### 语言风格

- 使用自然、克制的中文技术解说，重点解释目的、因果和结果，不逐字朗读按钮。
- `AgentVersion`、`EvalSuite`、`GateRun`、`new_failure`、`fixed` 等第一次出现时配中文解释，后文保持术语一致。
- 区分“测试通过”“达到本次套件阈值”“允许按当前策略发布”，不把它们扩大为“Agent 永远正确”。
- 明确说“本段使用确定性 Mock 验证工作流”，不说“Mock 证明真实模型准确率”。
- 失败段讲事实和定位线索；修复段讲修改及同集验证，不使用“智能体自己发现问题并修复”等未实现叙述。

### 合成规格
